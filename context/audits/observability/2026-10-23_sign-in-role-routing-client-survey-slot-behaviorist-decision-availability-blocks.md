# Observability audit — sign-in, booking, decision, blocks (2026-10-23)

## 1. TL;DR

- Session bootstrap treats a GoTrue or `profiles` failure as “nobody is signed in”, so an auth outage is a normal redirect to `/auth/signin` or `/`.
- Accept, reject, and block writes answer with 302/303 and a short query code. The Postgres error is dropped before any log line exists.
- Calendar, submission detail, and the client’s consultation list render a database error as HTTP 200.
- Slot and insert failures do return 500, but only `error.message` survives. The `cause` set on the thrown error is discarded, and nothing reports it.
- No application code initializes an error tracker or a logger. A throw becomes one console stack string inside Astro, then a normal 500 response. `Error.cause` is not in that string.
- A failed availability-block read does not look like an open calendar. `getAvailableSlots` throws. The booking page then hits Astro’s 500 path. The slots and insert APIs catch that throw and flatten it.

## 2. Capture model

Behawiorysta is an Astro 7 server app (`output: "server"`, `astro.config.mjs:11-12`) on Cloudflare Workers (`@astrojs/cloudflare`, `wrangler.jsonc:4`). Pages are server-rendered. Interactive pieces are React islands (`client:load`). There is no cron, queue, Durable Object, or `waitUntil` call under `src/`.

**Tracker.** The verified tree has no error-tracker init. `astro.config.mjs:12` registers `react()` and `sitemap()` only. `src/middleware.ts:12` is a plain `defineMiddleware`. A search of `src/` found no `captureException`, `console.error`, or `console.warn`. `package.json` does not depend on `@sentry/*`. There is no `sentry.client.config.js` and no `sentry.server.config.js`.

**What a failure can hit.**

- A throw from middleware or a page/endpoint is caught by Astro (`node_modules/astro/dist/core/routing/handler.js:101-108`). The logger writes `err.stack || err.message || String(err)` through `console.error` (`node_modules/astro/dist/core/logger/impls/console.js:11-21`). The Cloudflare entry returns that response (`node_modules/@astrojs/cloudflare/dist/utils/handler.js:79-87`). The Worker invocation is a handled 500. There is no `src/pages/500.astro`.
- A handler that returns a `Response` never enters that catch. `logRequestFromState` records method, pathname, and status (`handler.js:94-99`). The error object is not part of that line.
- A throw after the first streamed byte calls `controller.error(e)` and does not call the logger (`node_modules/astro/dist/runtime/server/render/astro/render.js:66-72`). Current consultation and dashboard reads run in frontmatter, so they still throw before the stream.
- The browser has no tracker script (`src/layouts/Layout.astro`) and no React error boundary.

**Logging.** The only serializer on the throw path is Astro’s stack string. `Error.cause` is not part of `.stack`.

**Scrubbing and sampling.** No `beforeSend`, no sample rate, no ignore list. Nothing builds an event to scrub.

**Deploy identity.** No release or environment tag is set in code, because no event is created.

**Assumptions (outside the repo, not findings):**

- Cloudflare Workers log collection is on. `wrangler.jsonc:12-14` sets `observability.enabled`. Unconfirmed that anyone alerts on those logs. Confirmed in repo as a flag only.
- Alert rules, a Sentry project, and source-map upload are unconfirmed. This commit does not call an SDK, so those settings would not receive the failures below.
- At 00:14 the working tree on `3f0674c` contained uncommitted client Sentry wiring (`sentry.client.config.js`, `@sentry/astro` with `server: false`, `PUBLIC_SENTRY_DSN` in `wrangler.jsonc`). That wiring is not in `3f0674c` or `c4ee1ad`, and it was absent when these findings were checked. Putting that client-only init back would still miss every finding that returns a response instead of throwing.

## 4. Systemic root causes

1. **Nothing in the app builds an error event.** `astro.config.mjs:12` never registers a tracker. `src/middleware.ts:12` is the only `onRequest`, and it does not report. Client layout never loads a script. Every later finding is invisible to an issue tracker for this reason, and the findings that return a normal response are also invisible to the console.

2. **Astro turns a throw into a response and a stack string.** `handler.js:101-108` logs `err.stack` and returns 500. The Cloudflare handler returns that response (`handler.js:79-87`). `cause`, the Supabase `code`, and the user id are not attached. This is the best signal the process has, and it only happens when something throws.

3. **Session bootstrap unwraps `data` and ignores `error`.** `middleware.ts:19-26` keeps `user` and `profile.role`. `@supabase/auth-js` returns network failures and HTTP 5xx as `AuthRetryableFetchError` on `{ error }` (`node_modules/@supabase/auth-js/dist/module/lib/fetch.js:115-120` and `:41-43`; `GoTrueClient.js:2716-2723`). `AuthSessionMissingError` uses the same `{ user: null, error }` shape for a normal signed-out request (`GoTrueClient.js:2706-2707`). PostgREST profile reads resolve `{ error }` and do not throw. Both a missing row and a failed read become `role === null` (`middleware.ts:8-9`, `role-routes.ts:8`).

4. **Failure responses keep a short token or a message and drop the error object.** `jsonError` (`consultation-api.ts:9-11`) returns `{ error: message }`. Decision and block handlers redirect. Page loaders set a boolean or `error.message` and render 200. Callers that had a `cause` (`availability.ts:16-20`) pass `error.message` into `jsonError` (`consultations/index.ts:31-33`, `slots.ts:14-16`).

5. **The browser swallows the one client catch.** `ConsultationForm.tsx:139-140` has no binding. `Layout.astro` loads no reporter. Hydration and chunk-load failures stay on that machine.

## 6. Recommended fix order

1. **Teach session bootstrap to tell “signed out” from “auth is down”.** Finding 2, and the missing-client half of finding 8. In `middleware.ts`, read `error` from `getUser()` and from the profile query. Do not report `AuthSessionMissingError`. For any other auth error, and for a profile `error`, capture `name` / `status` / `code` plus pathname and user id (never the email), and return 503. Keep the sign-in and home redirects for a real anonymous session and for a real missing role (`error === null`). This is the change that makes a GoTrue or `profiles` outage visible. A tracker wrapper alone will not see it, because these calls do not throw.

2. **Capture the `Error` object around `next()`.** Findings 1 and 7. `try/catch` in `onRequest`, `captureException` with route and user id, then rethrow. That turns today’s stack string into an issue and still lets Astro return 500. Do not also report the same throw from a second hook.

3. **One helper for handled server failures.** Findings 3, 4, 5, and 6. Before `jsonError(5xx, …)`, before `?decided=error` / `?block_error=save|delete` on a Supabase error, and before the three 200 banners, capture the Supabase `code`, `message`, `details`, and `hint`, plus the operation and the consultation id or day. Return a generic sentence to the browser and a 5xx for reads. Leave these unreported: 400 field validation, 409 / `23505`, `decided=unavailable`, block codes `date` / `empty` / `hour` / `duplicate`, and `invalid_credentials`. Do not attach survey fields, dog names, or email.

4. **Report the client submit failure and stop presenting a stale slot list as current.** Finding 9, and the browser half of finding 1. Init the client SDK from the layout. Bind the `catch` in `ConsultationForm` and report the error and the HTTP status. On a failed `refreshSlots`, show a reload error.

5. **Sign-out and the confirmation link.** Findings 10 and 12. Smaller, and they do not hide a booking or a decision.

6. **Stream failures.** Finding 11. Worth doing with the server boundary, and it is not on the path of today’s frontmatter queries.

Privacy: user id and consultation id are enough. Drop email, survey text, and raw provider messages. Keep error `name`, HTTP status, and Postgres `code`.
